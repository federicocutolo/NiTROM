# Cantilever-plate NiTROM example

NiTROM on the **3D linear-elastic cantilever plate** of Gruber, Tezaur &
Gunzburger ("Canonical and Noncanonical Hamiltonian Operator Inference"). Same
machinery and file layout as [`../wave_equation`](../wave_equation), adapted to a
much larger, externally-generated FOM.

## The model

A canonical linear Hamiltonian system, structurally identical to the wave case:

```
x = [q; p],   p = M q̇,   ẋ = J A x,   H = ½ xᵀ A x
J = [[0, I], [-I, 0]],    A = blkdiag(K, M⁻¹)
```

with finite-element mass `M` and stiffness `K`. The FOM is generated by Albany
(`mass.mm`, `stiff.mm`, the Exodus `.e`); the **training data is re-integrated**
from the IC by implicit-midpoint, not read raw. State dim is `~10⁴`
(`2·3·nodes`), so everything stays **sparse** and we never form a dense `M⁻¹` or
matrix exponential.

State layout matches the wave example: `X[:N] = q` (3 dofs/node, interleaved
x,y,z), `X[N:] = p`, with `N = 3·nodes`.

## No FOM class is needed

VC-H-OpInf and NiTROM consume only **data + velocities + `Φ` + `J`** — never a
FOM object. So this example has no `*_foms.py`. `W_fom = A` is saved (sparse)
*only* for the Petrov–Galerkin baseline and energy-drift diagnostics; energy is a
one-line `½ xᵀA x`, not a method.

## Pipeline / run order

Data arrives as a single pickled-dict `.npy` (the reference `plate_snaps.npy`)
with keys `x`, `x_test`, `xDot`, `A_sparse`, `J_sparse`. Then:

```
python prepare_data.py path/to/plate_snaps.npy   # -> NiTROM layout + Phi_cl/Phi_pod + W_fom
mpiexec -n 1 python -u train_nitrom.py           # ONE (BASIS, TENSOR) case per run
python test_nitrom.py                            # compares all trained cases for one BASIS
```

| File | Role |
|---|---|
| `prepare_data.py` | Adapter: reference dict → `traj_/deriv_/time/weight/Phi_cl/W_fom` + test set; builds the cotangent-lift basis. |
| `plate_cases.py` | Registry `get_case("cantilever")`; I/O folders + **sparse** `canonical_J`; NiTROM container helpers. |
| `plate_roms.py` | VC-H-OpInf + Petrov–Galerkin (copied from `wave_roms`, made sparse-`J`/`W` safe). |
| `train_nitrom.py` | Progressive-window Riemannian CG training of `(Φ, A2)`. |
| `test_nitrom.py` | FOM (loaded from disk) vs ROMs: relative error + energy drift + tip displacement. |
| `Bracket/{trajectories,output,test_results}/` | I/O. |

## NiTROM initialization cases (solution containers)

A NiTROM run is labeled by its **initialization**: the reduced basis it starts
from (`cl` cotangent-lift or `pod`) and the tensor seeding `A2` (`pg`
Petrov–Galerkin or `opinf` VC-H-OpInf). Each of the four combinations owns a
solution container, so runs never overwrite each other:

```
Bracket/
  trajectories/          # shared data (x, xdot, time, Phi_cl, Phi_pod, A_fom, ...)
  output/
    cl_opinf/            # NiTROM: CL basis,  VC-H-OpInf-seeded A2   (Phi_nit, A2_nit, ...)
    cl_pg/               # NiTROM: CL basis,  PG-seeded A2
    pod_opinf/           # NiTROM: POD basis, VC-H-OpInf-seeded A2
    pod_pg/              # NiTROM: POD basis, PG-seeded A2
  test_results/
    cl/                  # comparison plots, CL basis:  PG, VC-H-OpInf, NiTROM-PG, NiTROM-OpInf
    pod/                 # same four curves, POD basis
```

Workflow: set `BASIS`/`TENSOR` in `train_nitrom.py` and run once per case
(`RESTART = True` resumes that same container); then set `BASIS` in
`test_nitrom.py` — it builds the PG and VC-H-OpInf baselines for that basis,
loads whichever NiTROM containers are trained (missing ones are skipped with a
notice), and writes the four-curve `error_vs_time` / `energy_drift` /
`tip_disp` plots (basis named in the title) to `test_results/<basis>/`.

## Key differences from the wave example

- **No FOM class** — see above. Time vectors are derived from the snapshot count
  using the reference horizons (`T_train = 0.002`, `T_test = 0.005`).
- **Sparse end-to-end.** `J` and `W_fom` are kept sparse; `plate_roms` is
  reparenthesized (`Φᵀ (J Φ)`) so a dense `J` is never materialized.
- **`test_nitrom` loads the FOM trajectory** rather than re-integrating it — a
  dense `expm` on a `~10⁴`-dim operator is infeasible. Only the small `(2r×2r)`
  reduced ROMs are propagated.
- **Single trajectory** (`n_traj = 1`), so MPI is capped at **1 rank**. To
  parallelize, window the one trajectory into pseudo-trajectories (snapshot
  chunks as independent shooting segments) — the trajectory-parallel logic then
  applies unchanged.

## Knobs to set when data lands

- **`RANK`** in `prepare_data.py` — cotangent-lift modes per field (reduced dim
  `2·RANK`). The reference swept up to ~124; tune to your accuracy target.
- Confirm the dict keys match (`x`, `x_test`, `xDot`, `A_sparse`) — a one-line fix
  in `prepare_data.py` otherwise.
- `BASIS` (`cl` | `pod`) and `TENSOR` (`pg` | `opinf` | `random`) in
  `train_nitrom.py`; `RESTART = True` resumes the matching container.

## Why NiTROM may barely move from VC-H-OpInf

As in the wave case: for a linear, well-resolved problem OpInf already recovers
the (near-)exact reduced operator and the error is projection-dominated, so the
optimizer starts near-stationary. The plate is a transport-dominated problem with
a **flat** singular-value spectrum (slow Kolmogorov n-width), so expect a larger
`r` for accuracy — and that flatter regime is where NiTROM's basis optimization
has the most room to help.
